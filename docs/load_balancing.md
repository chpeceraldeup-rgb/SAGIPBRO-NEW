# SAGIPBRO deployment and load balancing

SAGIPBRO is plain PHP. Public pages read MySQL directly; protected screens use PHP sessions and JSON APIs. The development command `php -S` runs a single request worker and is unsuitable for production concurrency. Admin API reads often fetch entire tables, while public directories inspect `information_schema` once per request and render all matching rows. No production timings or traffic figures are available, so a performance root cause has not been established. Measure PHP worker utilization, p95 request duration, query plans, MySQL CPU/connection count, and browser network timings before adding nodes. If MySQL is saturated, two PHP servers can make the problem worse.

## Two-server design

```text
users -> HTTPS Nginx -> PHP server 1 or PHP server 2 -> one shared MySQL
                                         \                 /
                                          shared session table
```

`deploy/nginx.conf` uses `least_conn` to send each request to the less busy backend. Nginx passively marks a backend failed after two failed attempts within ten seconds, retries eligible requests on the other backend, and tries the failed backend again after the timeout. Nginx Open Source does **not** actively poll `/health.php`; monitor that endpoint on each backend separately. Never retry a non-idempotent POST after an ambiguous write. Neither Nginx nor PHP protects against loss of the single MySQL server or the single load balancer. This is a worker-capacity and PHP-node failover design, not complete high availability.

Both backends must use the same code revision, the same `SAGIPBRO_BASE_URL`, the same MySQL host/database, synchronized clocks, and compatible PHP extensions. Use Apache with PHP or PHP-FPM behind a web server in production. Bind backends to a private network; block direct public access and deny `/config`, `/database`, `/tests`, `/deploy`, `/java`, hidden paths, and the CLI setup script at the edge. The Nginx sample listens on HTTPS and redirects HTTP. Replace its example hostname, backend addresses, and certificate paths; run `nginx -t` before reload. Keep TLS certificates on the balancer, use TLS to MySQL where the network requires it, and use trusted internal TLS between Nginx and distant backends. Set `SAGIPBRO_TRUST_PROXY=1` only when clients cannot reach the backends directly; then login throttling, reCAPTCHA, and activity logs use Nginx's validated `X-Real-IP` header.

## Database and sessions

MySQL remains the single source of truth. Set `SAGIPBRO_DB_HOST`, `SAGIPBRO_DB_PORT`, `SAGIPBRO_DB_NAME`, `SAGIPBRO_DB_USER`, and `SAGIPBRO_DB_PASSWORD` identically on both servers. In production, all except port are required, and the application rejects `root` or an empty password. Put values in the service manager's protected environment or a secret manager, outside the web root; do not commit a `.env` with credentials. Grant the application user only the privileges needed for its business tables and `SELECT/INSERT/UPDATE/DELETE` on `sagipbro_sessions`. Use a separate migration account for DDL. The current volunteer API performs `CREATE TABLE IF NOT EXISTS` on requests, so remove that legacy behavior after verifying the target database has the table; until then its account may still need `CREATE`, which is a deployment limitation.

Run the additive session migration once against the selected database before enabling the shared driver:

```powershell
$env:SAGIPBRO_DB_NAME = 'sagipbro'
& 'C:\xampp\php\php.exe' database/migrate_shared_sessions.php
```

Set `SAGIPBRO_SESSION_DRIVER=database` on **both** nodes. `SAGIPBRO_ENV=production` makes that driver mandatory. The handler stores opaque session data in `sagipbro_sessions`; MySQL named locks serialize requests for one session ID, including requests routed to different PHP servers. Lock wait is five seconds. Do not use local file sessions in a two-node deployment and do not enable sticky routing as a substitute. The PHP cookie is HttpOnly, SameSite=Lax, and secure when PHP sees HTTPS or `SAGIPBRO_SECURE_COOKIES=1`. Set the latter to `1` when TLS terminates at Nginx. Production requires it. Login regenerates the session ID; POST logout verifies CSRF, destroys the stored session, and expires the cookie. Changing from file sessions logs out existing users. MySQL loss causes protected/session pages to return 503 rather than silently switching to local storage.

## Files, public data, and security

The repository has static images, CSS, and JavaScript but no file input or PHP upload handler. Browser-side CSV exports and server-side public CSV reports stream the response; they do not store reports on a PHP node. Deploy the same static assets on both nodes. Before adding user uploads, use object storage or a shared durable volume, store only a reference in MySQL, validate MIME/content and size, generate server-side names, and serve uploads outside executable PHP paths. A shared network filesystem is simpler but adds a central availability dependency; object storage scales better. Never keep upload files only on one backend.

Public disaster data has `no-store` responses so announcements, stock, and evacuation capacity are re-read. Cache only versioned static assets. Do not cache private APIs or operational inventory. CSRF tokens are in the session and accepted from forms or the `X-CSRF-Token` header. Protected requests recheck the account's active status and role against the shared database. Sensitive resident, volunteer, and distribution APIs require staff roles. PDO uses prepared values for writes and user filters; public SQL identifier choices come from a fixed schema map. Passwords use `password_hash()` and `password_verify()`. The current login throttle is session-scoped and can be bypassed by obtaining a new session; use a shared IP/account rate limiter at the edge before internet exposure. Several management pages still contain demo forms and blank `actions/*` handlers. Those are existing feature gaps, not verified CRUD functionality. The older APIs assume the alternate `sagipbro` columns and do not work with the repository's fresh-install schema without adaptation; verify the actual target schema before promising CRUD. Avoid displaying PHP errors (`display_errors=Off`) and send PHP, Nginx, and MySQL logs to central collection with request IDs and alerts for 5xx rates, slow requests, unavailable readiness, and DB lock waits. Logs must not contain passwords or full resident records.

## Local and production run

For one-node local development, start MySQL, set the selected database name, then run `php -S 127.0.0.1:8080 -t .`. File sessions remain the local default. To exercise the shared driver locally, run the session migration and set `SAGIPBRO_SESSION_DRIVER=database`; start two loopback PHP servers on ports 8081 and 8082 in separate terminals. The development server only simulates two application nodes; use Apache/PHP-FPM for capacity testing. Install Nginx separately, place `deploy/nginx.conf` inside its `http` context, replace the example hostname/certificate paths, and route to those ports. Set `SAGIPBRO_BASE_URL` to the public root URL or path on both backends. In production set `SAGIPBRO_ENV=production`, `SAGIPBRO_SECURE_COOKIES=1`, the shared session driver, and all database settings. Provision one centralized database and import or migrate the appropriate schema **once**, never one database per PHP server.

`/health.php` returns `200 ready` only if MySQL and the shared session table are reachable; otherwise it returns `503 unavailable`. It opens no PHP session and reports no connection details. A separate load balancer or monitor may use it as an active readiness check. The sample Nginx uses passive failure handling, so alert on each backend's readiness directly. A failed PHP backend can be routed around; a failed database cannot. Monitor and back up MySQL, and test restoration. To add PHP servers, deploy the identical release and environment to each, add its private address to the Nginx upstream, check readiness, then `nginx -t` and reload.

## Acceptance test procedure

Use a disposable copy of the production schema and test users. Run `php tests/shared_sessions_integration.php` against an isolated MySQL test server with CREATE/DROP DATABASE permission; it creates and removes only a randomly named test database. After the migration, verify login, session ID regeneration, logout and cookie expiry, CSRF rejection, admin/official/volunteer/resident authorization, and account deactivation while signed in. Exercise each working CRUD API and public announcements, resources, centers, distributions, residents, reports, and contact form; verify published records change on reload and private details stay private. Existing demo forms and zero-byte action handlers cannot pass a persistence test until separately implemented. Check database-off 503 behavior. With Nginx and both backends running, log in through backend 1, send the next request with the same cookie through backend 2, and verify identity and CSRF; then repeat through Nginx. Stop backend 1, then backend 2, one at a time, and confirm eligible GET requests continue and monitoring detects the failure. Test `/health.php` on each backend and observe Nginx's passive failover. Use a traffic generator with independent sessions for simultaneous users; compare p50/p95 latency, PHP worker saturation, and MySQL load with one and two nodes. There is no upload workflow to test in the current application. Do not label the system high availability until these tests, database recovery, and balancer recovery have passed in the actual deployment.

For query tuning, run `EXPLAIN ANALYZE` against representative data first. Candidate indexes include `activity_logs(created_at)`, `distributions(distribution_date, resource_id)`, `announcements(status, published_at, expires_at)`, and `resources(status, category, resource_name)` for the alternate schema. Check existing indexes before adding any; the migration deliberately changes no business tables. Full-table API reads need bounded pagination when row counts justify it. Compare query and browser timings before introducing such behavior changes.
